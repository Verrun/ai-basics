# Ф1. Как устроено приложение: фронтенд, бекенд, API и база данных

## За 2 минуты

Любое приложение можно представить как ресторан. **Frontend** (фронтенд) — «лицо» сайта: кнопки и экраны, которые видит пользователь. **Backend** (бекенд) — «кухня»: логика и расчёты на сервере, которые никто не видит. **API** — официант с меню: договорённость, какими словами фронтенд может «заказать» у кухни. **База данных (database)** — склад продуктов, где всё хранится. Один клик по кнопке — это целый обход: экран → официант → кухня → склад → и обратно.

---

## Простыми словами

Представь ресторан.

**Ты — гость** за столом. Перед тобой меню, и ты нажимаешь кнопку «заказать». Это **frontend**: красивый зал, стол, меню. Гость не видит ни кухню, ни склад — и ему это не нужно.

**Официант** подходит к столу. Он не готовит еду и не хранит продукты — он знает **правила обмена**: как принять заказ и в каком виде его отнести на кухню и вернуть к столу. Это **API**: не приложение и не база, а **договор** о том, какими словами можно попросить и что получишь в ответ. «Окошко выдачи» у кухни — это **endpoint**: конкретное место, куда стучаться за конкретной вещью (заказы — сюда, счёт — туда).

**Кухня** получает заказ, готовит, проверяет («нет, сырых креветок не отдадим»), считает. Это **backend**: вся логика и правила, которые спрятаны от гостя.

**Склад** — комната с продуктами: рис, вода, тортики. Это **база данных**: всё, чем приложение владеет, лежит именно там, а не в зале и не у официанта.

Теперь прогони полный цикл:

1. Ты жмёшь в меню «заказать пасту» (frontend).
2. Официант записывает заказ ровно в том виде, в каком кухня его понимает (API).
3. Кухня смотрит рецепт, считает цену, проверяет, что пасту можно дать (backend).
4. Повар идёт на склад за макаронами и соусом (база данных).
5. Кухня отдаёт блюдо официанту в «форме выдачи» — на подносе (API снова).
6. Официант несёт тебе пасту, зал обновляется: на столе появляется блюдо (экран обновился).

Весь интернет устроен так же: **ты видишь только зал, а ресторан работает за кадром**.

## Объяснение

### Frontend — лицо приложения

**Термин:** **frontend** (фронтенд, «передняя часть») — всё, что работает **в браузере у пользователя**: кнопки, формы, анимации, тексты.

Три кита фронтенда:

| Технология | Роль | Аналогия |
|------------|------|----------|
| **HTML** | Структура страницы | Скелет, каркас дома |
| **CSS** | Внешний вид: цвета, шрифты, отступы | Одежда и макияж |
| **JS** (JavaScript) | Поведение: что происходит по клику | Мышцы и движения |

Фронтенд сам **ничего не хранит**: закрыл вкладку — всё «забыл». Если в ресторане погас свет в зале, еда на кухне никуда не делась.

### Backend — кухня за кадром

**Термин:** **backend** (бекенд, «задняя часть») — программа на **сервере**, которую пользователь никогда не видит.

| Backend делает | Пример |
|----------------|--------|
| Проверяет правила | «Нельзя перевести сумму больше, чем на счету» |
| Считает | Скидка, налог, итог корзины |
| Решает, что показать | Тебе — твои письма, соседу — свои |
| Говорит «да» или «нет» | Пароль верный → пускаем |

Пользователь может хоть сто раз кликать по кнопке — если кухня говорит «нет», кнопка не поможет. Поэтому «всё сломалось» чаще всего означает: **сломалась кухня**, а не зал.

### API — официант с меню

**Термин:** **API** (Application Programming Interface, «интерфейс для программ») — **договор** о том, как одна часть системы может попросить что-то у другой и в каком виде получит ответ.

**Термин:** **endpoint** (эндпоинт, «точка входа») — конкретное «окошко» API с адресом. Как в ресторане: окошко «выдача заказов», окошко «оплата счёта» — разные адреса для разных дел.

Примеры осмысленных адресов: `/users` (пользователи), `/orders` (заказы), `/login` (вход).

Важно: API — это **не приложение и не программа**. Это **правила разговора**. Официант — не кухня и не склад, а способ между ними.

### База данных — склад, а не папка

**Термин:** **база данных (database, БД)** — место, где приложение **хранит** свою информацию: пользователей, заказы, письма.

| | Файлы (папка на диске) | База данных |
|--|------------------------|-------------|
| Что там | Документы, фото, PDF | Записи: «пользователь №5: Аня, заказы: 3» |
| Как устроено | Просто лежат | Специальная программа (СУБД), которая умеет **быстро искать и связывать** |
| Аналогия | Коробка с бумагами на чердаке | Картотека с индексами в архиве |
| Сколько может | Десятки | Миллионы записей — и мгновенно |

Если погас свет в зале (frontend сломался) или уволился официант (API), склад цел. Данные живут **отдельно от экрана** — поэтому твои письма не исчезают, когда ты закрываешь браузер.

### Путь одного клика

Клик по кнопке «Купить» — это не одно действие, а **цепочка**:

| Шаг | Кто | Что делает | В ресторане |
|-----|-----|------------|-------------|
| 1 | Ты | Жмёшь кнопку | Гость выбирает в меню |
| 2 | Frontend | Собирает данные (что, сколько) и отправляет запрос | Официант записывает заказ |
| 3 | API | Принимает запрос по правилам и передаёт дальше | Официант несёт бланк на кухню |
| 4 | Backend | Проверяет правила, считает цену | Кухня готовит и считает |
| 5 | База данных | Отдаёт нужные данные / сохраняет заказ | Повар берёт продукты со склада |
| 6 | Backend | Формирует ответ | Кухня отдаёт блюдо |
| 7 | API | Возвращает ответ фронтенду | Официант несёт поднос |
| 8 | Frontend | Обновляет экран: «Заказ оформлен» | Блюдо появляется на столе |

Все восемь шагов занимают **доли секунды**. Но когда что-то ломается, ломается ровно один из них — и понимание цепочки подскажет, куда смотреть (это пригодится в Ф9 про отладку).

### Кто за что отвечает: шпаргалка

| Термин | Метафора | Одной фразой |
|--------|----------|--------------|
| **Frontend** | Лицо | Всё, что ты видишь и трогаешь |
| **Backend** | Мозг и руки | Думает, проверяет, считает — за кадром |
| **API** | Официант с меню | Правила, как просить и как получать |
| **База данных** | Память и склад | Хранит всё, что приложение знает |

### Частые ловушки

1. **«Бекенд — это интернет»** — нет. Интернет — это дороги между ресторанами. Бекенд — кухня внутри одного конкретного ресторана.
2. **«API — это приложение»** — нет. API — договор/официант, а не программа сама по себе. У одного бекенда может быть много API-«окошек».
3. **«База данных — это папка с файлами»** — нет. Это отдельная программа, которая умеет мгновенно искать и связывать миллионы записей. В Ф4 разберём SQL.
4. **Путать клиента и сервер** — клиент = твой браузер (гость), сервер = чужой компьютер в дата-центре (ресторан). Браузер ничего не «знает», он только показывает.
5. **Думать, что фронтенд хранит данные** — закрой вкладку: фронтенд всё забудет. Всё живёт на сервере и в базе.
6. **Судить о приложении по картинке** — если кнопка не работает, проблема может быть на любом из 8 шагов, а не «на сайте вообще».

## Практика

Никакого кода не нужно — только внимательный взгляд.

1. Открой любой сайт, где ты залогинена: почту, банк или интернет-магазин.
2. Ответь письменно (в заметке): что здесь **frontend**? Перечисли 3 элемента, которые ты видишь.
3. Нажми кнопку, которая что-то «делает» (например, «Обновить» или «Поиск»), и заметь: **экран на мгновение «думает»**. Это цепочка из 8 шагов — где она могла задержаться?
4. Закрой вкладку и открой сайт заново. Твои данные на месте? Кто их хранил, пока вкладка была закрыта? (Подсказка: не зал и не официант.)
5. Для одного из сервисов, которыми ты пользуешься, выпиши по одной строке: кто тут «клиент», кто «сервер», что лежит в «складе».

## Частые ошибки

1. **Путать API и backend** — backend готовит, API только передаёт заказы и ответы. Это официант, а не повар.
2. **Думать, что «красиво работает» = «правильно работает»** — зал может выглядеть отлично, пока кухня отдаёт ошибки. Красивый экран не гарантирует правильную логику.
3. **Искать данные «в сайте»** — данные не в сайте, а в базе на сервере. Сайт лишь показывает их копию на экране.
