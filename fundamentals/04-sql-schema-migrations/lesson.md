# Ф4. SQL, связи в базе данных, схемы и миграции

## За 2 минуты

Помнишь из Ф1: **база данных (БД)** — это «склад» приложения, где лежат все данные? Этот урок — про то, как устроен склад внутри. Данные лежат в **таблицах**, по ним ходят запросы на языке **SQL**, таблицы связаны **ключами** (key), а план всего склада называется **схемой (schema)**. Изменять план «просто руками» нельзя — для этого есть **миграции (migrations)**, пронумерованные шаги перестройки склада.

---

## Простыми словами

Представь большую библиотеку.

Там есть **стеллажи** — это **таблицы**. Один стеллаж для читателей, другой — для книг, третий — для заказов.

На каждом стеллаже лежат **карточки** — это **строки (rows)**. Одна карточка = один читатель.

На каждой карточке напечатаны **поля**: имя, дата регистрации, номер билета. Это **колонки (columns)**. У всех карточек на стеллаже поля одинаковые — иначе их невозможно было бы сортировать.

Теперь ты подходишь к стойке администратора и просишь: «Покажи всех читателей, кто зарегистрировался в этом месяце». Администратор ходит на стеллаж и приносит нужные карточки. Язык, на котором ты вежливо просишь, — это **SQL**. Ты не лезешь сама на стеллаж — ты формулируешь запрос.

А у архитектора библиотеки есть **план здания**: где какие стеллажи стоят и как они связаны между собой. Этот план — **схема (schema)**. Если библиотеке нужен новый стеллаж или приходится переименовать поле на карточке, это делается по **журналу ремонтов** — каждая перестройка записывается с номером. Это **миграции**. Так все филиалы библиотеки делают одни и те же изменения в одном порядке и ничего не теряют.

## Объяснение

### Таблицы, строки, колонки

| Термин | В библиотеке | В базе данных |
|--------|--------------|---------------|
| **Таблица (table)** | Стеллаж с карточками | Набор данных об одном типе объектов |
| **Строка (row)** | Одна карточка | Одна запись (один читатель, один заказ) |
| **Колонка (column)** | Поле на карточке | Одно свойство (имя, дата, сумма) |
| **Схема (schema)** | План здания | Какие таблицы есть и как связаны |

### SQL — язык вежливых просьб

**SQL** (*Structured Query Language* — «язык структурированных запросов») — единый язык, на котором просят данные из базы. Четыре команды покрывают почти всё повседневное:

| Команда SQL | Перевод | Бытовая аналогия |
|-------------|---------|------------------|
| **SELECT** | Покажи | «Принеси мне карточки всех, кто…» |
| **INSERT** | Добавь | «Заведи новую карточку на полку» |
| **UPDATE** | Измени | «Допиши на карточке новый адрес» |
| **DELETE** | Удали | «Выкинь эту карточку» |

Пример (учить наизусть не нужно — Agent запускает SQL за тебя):

```sql
SELECT имя, дата FROM читатели WHERE дата >= '2026-09-01';
INSERT INTO читатели (имя, дата) VALUES ('Аня', '2026-09-15');
UPDATE читатели SET имя = 'Анна' WHERE id = 7;
DELETE FROM читатели WHERE id = 7;
```

### Ключи: как карточки ссылаются друг на друга

**Primary key (первичный ключ)** — уникальный номер записи. Аналогия: **номер читательского билета** — свой у каждого, не повторяется. По нему запись находится однозначно.

**Foreign key (внешний ключ)** — ссылка из одной таблицы на запись в другой. Аналогия: **пометка на карточке книги «взял читатель №123»** — карточка книги не хранит всю карточку читателя, а просто указывает на неё.

### Связи между таблицами

| Связь | Аналогия | Пример в приложении |
|-------|----------|---------------------|
| **Один-к-одному** | Человек ↔ его паспорт | Пользователь ↔ профиль с настройками |
| **Один-ко-многим** | Автор ↔ его книги | Клиент ↔ его заказы |
| **Многие-ко-многим** | Студенты ↔ курсы | Теги ↔ заметки (у заметки много тегов, у тега много заметок) |

Многие-ко-многим удобно развязывать **промежуточной таблицей** — как журнал записи: «студент №5 записан на курс №3».

### Схема (schema) — план склада, а не черновик

**Схема** — это договорённость о структуре: какие таблицы есть, какие у них колонки и как таблицы связаны. Схема важна потому, что:

- приложение **ждёт** данные в определённом виде — если ты молча переименуешь колонку, программа не найдёт её и упадёт;
- **несколько копий** базы существуют одновременно: на твоём ноутбуке, на тестовом сервере, в «проде» (боевом) — у всех должен быть одинаковый план склада;
- данные **не исчезают сами** — если удалить колонку руками, её содержимое удалено навсегда.

### Миграции: журнал ремонтов, а не «перекрасили стены ночью»

**Миграции (migrations)** — пронумерованные, повторяемые шаги изменения схемы: «добавили стеллаж», «переименовали колонку», «создали промежуточную таблицу». Каждый шаг записывается в журнал с номером версии.

Аналогия: библиотечный **журнал ремонтов**. «7 сентября: добавили стеллаж К-12 в зал №2. 10 сентября: поле „телефон“ на карточках переименовали в „мобильный“». Каждый филиал выполняет записи в том же порядке — и везде склад становится одинаковым.

Почему нельзя «просто поменять руками в проде»:

- **потеря данных** — без миграции никто не перенесёт старое содержимое в новую структуру;
- **расхождение у коллег** — твой ноутбук знает про новую колонку, прод — нет, у коллеги — третий вариант;
- **невозможно откатиться** — миграция обратима по журналу, ручная правка «как было — уже не помню».

### Частые ловушки

1. **Путать строку и колонку** — строка это одна карточка, колонка это поле на всех карточках сразу.
2. **Думать, что DELETE без условия безопасен** — `DELETE FROM читатели;` без WHERE удаляет *все* карточки, а не одну.
3. **Менять схему без миграции** — руки чешутся «быстро поправить в проде»; это путь к расхождению копий и потере данных.
4. **Хранить всё в одной таблице** — «одна карточка на всё» быстро превращается в кашу; связи существуют именно чтобы этого избежать.
5. **Путать foreign key с копией данных** — ссылка «карточка №123» не копирует данные читателя; если читатель сменил адрес, ссылка всегда покажет актуальное.
6. **Думать, что SQL — это программирование, которое надо учить** — базовые команды понять легко, а писать сложные запросы тебе не обязательно: Agent составит и запустит их за тебя.

## Практика

1. Представь приложение для записи к парикмахеру. Выпиши на листке бумаги 3 таблицы (например: клиенты, мастера, записи) и для каждой — 3–4 колонки. Для каждой таблицы отметь, какая колонка будет **primary key**, и покажи стрелочками **foreign key** между таблицами.
2. Определи типы связей: «клиент ↔ записи» — какая это связь? «клиент ↔ мастера» (через записи) — какая? Сверься с таблицей связей выше.
3. Открой терминал и попробуй SQLite — это база данных в одном файле, ничего устанавливать не надо (есть на macOS и Linux):

```bash
sqlite3 salon.db
```

```sql
CREATE TABLE клиенты (id INTEGER PRIMARY KEY, имя TEXT);
INSERT INTO клиенты (имя) VALUES ('Аня');
SELECT * FROM клиенты;
```

4. Попробуй команду с условием: `SELECT * FROM клиенты WHERE имя = 'Аня';` — и заметь разницу с SELECT без WHERE.
5. Напиши «журнал ремонтов» на бумаге: какие 2–3 миграции понадобились бы, если бы ты решила добавить таблицу «услуги» и поле «цена» к записям.

## Частые ошибки

1. **«Поправлю прямо в базе на проде, быстрее будет»** — быстрее сегодня, а завтра у тебя три разных склада вместо одного и потерянные данные.
2. **DELETE без WHERE «на всякий случай»** — случай наступает: условие WHERE это фильтр «какие именно карточки», без него задание звучит как «все».
3. **Скриншот таблицы вместо структуры** — когда просишь помощи, покажи схему (какие таблицы и колонки), а не картинку с данными.
