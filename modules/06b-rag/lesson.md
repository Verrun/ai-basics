# М6b. RAG-поиск

## За 2 минуты

**RAG** — модель сначала **ищет** нужные куски в *твоих* документах, потом отвечает по ним. Не «из головы», а по шпаргалке. Для смыслового поиска часто ставят локальную модель **e5-small**. Качество поиска проверяют по **golden set** — эталонным вопросам с правильными кусками.

---

## Простыми словами

Представь: у тебя на полке лежит папка с инструкциями компании. Ты спрашиваешь: «Какой у нас дедлайн по отчёту?»

Без RAG модель отвечает «из памяти» — может красиво выдумать.  
С RAG система делает так:

1. Берёт твой вопрос.
2. Находит **2–5 самых похожих абзацев** из твоих файлов.
3. Кладёт их рядом с вопросом как шпаргалку.
4. Модель отвечает **по этой шпаргалке** (и лучше — со ссылкой на файл).

Это и есть **RAG** = *Retrieval-Augmented Generation*  
(*поиск + дополнение + генерация*).

**Аналогия:** библиотекарь достаёт нужные страницы из *твоей* полки и кладёт их на стол — писатель читает их и только потом пишет ответ.

## Объяснение

### Зачем RAG, если есть интернет и чат

| Способ | Откуда знание | Когда уместно |
|--------|---------------|---------------|
| **Только LLM** | «Память» модели | Идеи, черновики, пересказ того, что уже в чате |
| **Поиск в интернете** (М6) | Сайты снаружи | Новости, тренды, чужие статьи |
| **RAG** | *Твои* PDF, Notion, vault, база знаний | Регламенты, FAQ продукта, внутренние гайды |

RAG не заменяет fact-check и не делает модель «всезнающей». Он даёт ей **доступ к нужным кускам твоих материалов**.

### Как устроен пайплайн (без кода)

1. **Документы** — PDF, markdown, Notion, заметки Obsidian.
2. **Нарезка (chunks)** — длинный текст режут на короткие куски (абзацы/страницы).  
   *Почему:* в запрос нельзя впихнуть всю энциклопедию сразу.
3. **Смысловой отпечаток (embedding)** — каждый кусок превращают в набор чисел «о чём это».  
   *Аналогия:* не ключевое слово «отчёт», а «похоже по смыслу на дедлайны и отчётность».
4. **Индекс / векторное хранилище** — полка, где лежат эти отпечатки, чтобы быстро искать похожее.
5. **Вопрос → поиск** — система находит ближайшие куски.
6. **Ответ** — модель генерирует текст **с опорой на найденное**.

Тебе не нужно писать этот пайплайн руками. Важно понимать **порядок**: сначала найти, потом отвечать.

### Chunk, embedding, индекс — коротко

| Термин | Простыми словами |
|--------|------------------|
| **Chunk** | Кусок текста (не весь файл целиком) |
| **Embedding** | «Смысловой отпечаток» куска — числа, по которым ищут похожее |
| **Индекс / vector store** | Склад отпечатков + быстрый поиск «что рядом по смыслу» |
| **Retrieval** | Шаг «найти куски» |
| **Augmented generation** | Шаг «ответить, глядя на найденное» |

### RAG vs «закинуть весь PDF в чат»

| | Весь файл в чат | RAG |
|--|-----------------|-----|
| Маленький PDF (5–10 стр.) | Часто ок | Избыточно |
| Сотни страниц / много файлов | Не влезет / дорого | Как раз для этого |
| Ответ | Может «потерять» середину | Тянет только релевантное |
| Повторные вопросы | Каждый раз грузить заново | Индекс живёт отдельно |

**Правило:** один короткий документ — приложи к чату. Библиотека документов — RAG (или vault + MCP, который умеет искать).

### Где ты уже встречаешь похожее

- **Cursor** по коду проекта: ищет нужные файлы, потом правит — идея та же, что у RAG (сначала найти контекст).
- **Obsidian + MCP:** AI читает vault; хороший поиск по заметкам ≈ «домашний RAG».
- **ChatGPT / Claude с Knowledge / Projects:** загружаешь базу — сервис сам режет и ищет.
- **Корпоративные боты** «спроси HR-бота» — почти всегда RAG по внутренним PDF.

### Локальная модель e5-small

**Термин:** `intfloat/multilingual-e5-small` (коротко **e5-small**) — маленькая модель **эмбеддингов**: превращает текст в смысловой отпечаток.  
**Аналогия:** *не писатель и не собеседник, а библиотекарь с «носом» на похожий смысл* — она не пишет ответ, а помогает **найти** нужные абзацы.

**Чем занимается (функции):**
- строит embeddings для **документов** (chunks) и для **вопроса**;
- сравнивает их по смыслу («насколько рядом»);
- умеет **несколько языков**, в том числе русский;
- работает **локально** на ноутбуке — тексты не обязательно слать в облачный чат;
- в RAG стоит на шаге **retrieval**, а отвечает уже другая LLM (ChatGPT, Claude, локальная чат-модель).

**Чего не делает:** не пишет письма, не «знает факты», не заменяет fact-check.

#### Как установить (простыми шагами)

Нужен Python 3. На курсе команды может выполнить **Agent в Cursor** — тебе важно понимать *зачем*, а не запоминать флаги.

1. Открой терминал в Cursor (или попроси Agent).
2. Установи библиотеку для эмбеддингов:

```bash
pip install sentence-transformers
```

3. Первый запуск скачает веса модели с Hugging Face (разово, сотни МБ). Пример проверки:

```bash
python3 - <<'PY'
from sentence_transformers import SentenceTransformer
model = SentenceTransformer("intfloat/multilingual-e5-small")
print("e5-small готова:", model.get_sentence_embedding_dimension(), "чисел в отпечатке")
PY
```

4. В реальном RAG-проекте после установки обычно запускают скрипт вроде «собери embeddings по корпусу» (у вас в пайплайне это шаг после ingest документов). Повторные прогоны могут идти **offline** из локального кэша — без новой загрузки.

**Важно для e5:** у этой семьи моделей текст помечают ролями — вопрос как `query: …`, кусок документа как `passage: …`. Иначе поиск слабее. Это делает код/скрипт; тебе достаточно знать, что «сырой» текст и «правильный формат e5» — разные вещи.

| | e5-small | Чат-модель (LLM) |
|--|----------|------------------|
| Роль в RAG | Найти похожие куски | Сгенерировать ответ по кускам |
| Пишет текст человеку | Нет | Да |
| Куда ставят | Локально / на своём сервере | Облако или локально |
| Размер | Маленькая, «small» | Обычно гораздо больше |

### Golden set для RAG

**Термин:** **golden set** (золотой набор) — небольшой набор **эталонных кейсов**: вопрос + какие куски документов *должны* найтись.  
**Аналогия:** *ответы в конце учебника* — по ним проверяешь, не разучилась ли система искать, когда ты поменяла нарезку, модель или ранжирование.

**Зачем собирают:**
- понять, **находит ли retrieval** правильные абзацы (ещё до красивого ответа LLM);
- поймать **регрессию**: вчера находило, после смены e5/чанков — перестало;
- договориться о **пороге качества** (baseline): ниже — стоп, чиним, а не «кажется ок»;
- отделить «плохой поиск» от «LLM выдумала» — разные поломки.

**Не путать:** golden set для **поиска** (нашлись ли нужные куски) и эталон для **ответов** (хорошо ли сформулирован финальный текст) — это два разных чеклиста. Сначала обычно стабилизируют поиск.

#### Как проходит сборка (по шагам)

1. **Корпус готов** — документы нарезаны, у кусков есть стабильные id, индекс (и при семантике — embeddings, например от e5-small) собран.
2. **Выбрать 10–20 реальных вопросов** — как спрашивают люди, не «идеальные» формулировки из ТЗ. Разные темы и сегменты аудитории, если они есть.
3. **Для каждого вопроса вручную найти правильные куски** в корпусе (прочитать глазами). Записать id этих кусков как `expected` — «вот что *должно* быть в top-k».
4. **Черновик (`draft`)** — агент или коллега могут предложить разметку, но пока статус draft: метрики скорее **предупреждают**, а не валят всё подряд. Битые id (нет в индексе) — всегда ошибка.
5. **Прогон eval** — скрипт по каждому вопросу запускает поиск и считает, попали ли ожидаемые куски в top-k (часто смотрят precision / recall / MRR).
6. **Ручной review** — владелица базы проверяет: вопрос понятен? куски *по смыслу* отвечают? ничего важного не забыли? спорное — в заметку или выкинуть.
7. **Апрув** — убрать `draft`, зафиксировать baseline. Дальше падение метрик = сигнал чинить retrieval, а не «подогнать порог молча».
8. **Только после апрува** имеет смысл включать более сложный режим поиска (например hybrid: ключевые слова + e5) как режим по умолчанию.

Мини-формат одного кейса (идея, не обязательно JSON):

| Поле | Пример |
|------|--------|
| Вопрос | «Какой дедлайн сдачи отчёта?» |
| Ожидаемые куски | id абзаца из регламента с датой |
| Заметка | «Сознательно не берём старый приказ 2019» |

### Частые ловушки

1. **Плохие документы** — мусор на входе → мусор в ответе. RAG не чинит кривые регламенты.
2. **Слишком крупные chunks** — находит «почти то», но тонет в лишнем тексте.
3. **Нет ссылок на источник** — проси: «цитируй файл и абзац»; иначе снова галлюцинации.
4. **Путать с веб-поиском** — RAG ≠ интернет. Для новостей — М6; для внутренних правил — RAG.
5. **Путать e5-small с чат-ботом** — e5 только ищет по смыслу; отвечает другая модель.
6. **Апрувить golden set не глядя** — шумная разметка → ложные падения или давление «завысить» пороги.

## Практика

1. Открой [exercises/rag-brief.md](../../exercises/rag-brief.md).
2. Собери **мини-базу** из 3–5 своих текстов (заметки, FAQ, выдержки из гайда — без секретов).
3. Задай один и тот же вопрос:
   - **без** документов (только модель);
   - **с** документами (чат с файлами / Cursor / Obsidian MCP).
4. Сравни: откуда факты, есть ли выдумки, удобно ли найти источник.
5. **Опционально (e5 + golden):** если ставишь локальный поиск — установи `sentence-transformers` и проверь, что e5-small загружается (блок выше). Затем составь **3 эталонных вопроса** к своей мини-базе и для каждого выпиши, *какой абзац* должен находиться — это заготовка golden set.

---

## Частые ошибки

1. **Ждать правду «потому что RAG»** — если кусок не нашёлся, модель всё равно может додумать.
2. **Кормить паролями и ПДн** — те же правила конфиденциальности, что в М1.
3. **Делать RAG ради RAG** — для одного письма в чат достаточно прикрепить файл.
